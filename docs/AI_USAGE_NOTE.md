# Entregable 3 — AI Usage & Decision Note

**Herramientas y uso.** Claude (chat con ejecución de código) para analizar el enunciado y generar la primera versión del dominio, la API NestJS y los tests. Claude Code (con BMad) en una segunda pasada para revisar críticamente lo generado, refactorizar en capas y completar los tests.

**Qué corregí, rechacé o acepté, y cómo lo validé.**
- **Endpoints que respondían 500.** La primera versión dejaba escapar los errores de las tools como 500. Le pedí mapearlos: cada lectura fallida o con timeout se convierte en un resultado controlado (`HUMAN_REVIEW` con su motivo, o `REJECTED` al confirmar) y la entrada inválida en 400. También detecté que la API usaba el reloj real contra fixtures fechados 2026-09-15 y siempre respondía `EVENTS_FEED_STALE`, aunque tests y demo pasaban. Lo validé con `curl` contra la API.
- **Tests: 38 en verde, pero sin explicación y con relleno.** No los tomé como fuente de verdad. Verifiqué los fixtures contra el enunciado y mapeé cada test al requisito que cubre. Eliminé el relleno (un assert vacío, dos tests duplicados) y endurecí aserciones laxas. Agregué los requisitos que faltaban (422 de `notify_passenger`, bordes de R1 y R2, PII en la capa de datos). Para cada test nuevo comprobé que detecta el error **rompiendo el código a propósito** (5 de 5 mutaciones detectadas).
- **Separación en capas.** Le pedí separar las capas como lo hacemos en LATAM: una *business layer* con las reglas de negocio (`src/domain`, pura y sin dependencias externas) y otra de acceso a APIs y llamados externos (`src/data`: contratos de las tools, mappers, timeouts). Los mappers descartan la PII en el borde, así que el dominio nunca la ve. Lo validé con las mismas aserciones antes y después y comparando la salida de la demo.
- **Code review asistido: contradicciones y un fallo de seguridad.** La revisión encontró contradicciones entre lo que el README prometía (fail-closed, control humano) y lo que el código y sus tests aceptaban. La más grave: en `rebooking-confirmations` **cualquier `caseId` enviado por el cliente autorizaba la reprogramación**, saltándose la validación humana de R5. Además, `?act=true` devolvía un `caseId` real reutilizable, y un test daba ese comportamiento por correcto. Lo reproduje con `curl`. **Lo rechacé**: si la política exige aprobación humana, el endpoint del pasajero siempre rechaza y la reprogramación la ejecuta un agente desde backoffice. No hay tool para consultar un caso, así que el servidor no puede verificar una aprobación enviada por el cliente.
- **Segunda revisión con `bmad-review`** (lentes adversarial, edge cases y verification gap) sobre el código final: reproduje los hallazgos antes de actuar. Corregí los que contradecían lo que afirma la entrega: un REFUND podía ejecutarse por `create_rebooking_request`; eventos malformados o con estado desconocido de una fuente confiable terminaban en silencio (`NO_ACTION`); opciones con TTL incalculable no vencían; el reloj fijo de los mocks podía combinarse con tools reales. Cada corrección tiene su test, validado rompiendo el código. El resto (autenticación, idempotencia de `act`, husos horarios) quedó documentado como riesgo.
- **Rechazado o evitado:** `eval` para evaluar condiciones, un agente LLM orquestador e IA de cara al pasajero (riesgo de prompt injection).

**Decisiones que tomé personalmente.** Track Backend. Cero IA en runtime. **Si no tenemos datos confiables, derivamos a humano**: cuando el estado de un tramo solo lo informa una fuente degradada, no se asume "sin novedad" (`NO_TRUSTED_SOURCE`). Queda pendiente un **spike para definir la fuente de verdad** de los datos operacionales (qué sistema es autoritativo por tipo de evento y qué hacer con fuentes como LEGACY_MIRROR). Reprogramación con R4/R5 solo desde backoffice. Conflicto entre fuentes confiables → humano. R5 interpretada como "toda acción pasa por una persona". Umbral de 60 min y MCT de 45 min como supuestos.

**Qué nunca entregaría a un modelo ni al cliente/usuario.** Email, teléfono, documento de identidad, nombres de pasajeros, datos de pago, credenciales o tokens, y reservas reales; solo fixtures sintéticos del enunciado. En runtime ningún dato de reserva sale hacia un modelo (no hay modelo).
